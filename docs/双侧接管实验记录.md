# 手势接管：实验记录

本分支保留旧版全高 Shizuku 实验、200dp 手柄优先模式，并新增 0.6.3-dev 临时扩大额度的替换模式。旧版全高入口仍仅对调试模拟器显示；新替换模式可从设置进入，默认不启用，尚待 OPPO 真机验收。下方日期区分各阶段证据，不能把旧模式的 OPPO 结果当作新模式通过。已发布的 v0.6.1 仍使用内移共存。

## 0.6.3-dev：大范围临时替换（2026-11-07）

入口为「设置 → 替换系统侧边手势」。没有继续扩大“返回热区缩放参数设为 0”的旧方案，而是临时提高 `android/system_gesture_exclusion_limit_dp`。独立 Shizuku shell UserService 只接受本应用 UID、固定设置键及有界数值，不提供任意命令接口；读取原值并在本机私有、不参与备份的记录中持久保存后，才申请额度。除配置读回，还检查 WindowManager 已应用新额度；默认主手柄覆盖可用侧边。

这个设置是全局额度，其他窗口的可申请上限也会受影响。它本身不关闭系统返回；系统是否让出某个位置，仍取决于当前存在的应用窗口及实际批准的排除区域。Android 16 对应实现见 [WindowManagerConstants](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android16-release/services/core/java/com/android/server/wm/WindowManagerConstants.java)。200dp 是普通配置下的额度，不应再表述为所有方案都不能突破的绝对上限。

在专用 API 36 模拟器（1080 × 2400、420 dpi）上，应用通过实际 Shizuku API 建立 1000dp 临时额度；左右批准区域为 `(0,63)-(63,2316)` 与 `(1017,63)-(1080,2316)`。每侧实际高度 2253px，约 858dp，覆盖屏幕高度约 94%，顶部和底部强制区域保留。此前 200dp 模式每侧为 525px。这次不是仅检查参数，也没有在宿主脚本中先设置 1000dp 来代替应用申请。

试用必须由用户开启，60 秒内从左右真实边缘各执行一次返回，再明确确认；试用不执行其他已配置动作。会话同意仅在当前进程中有效。高度另存为手柄的替换参数，0 表示该手柄停用，不生成内移窗口。恢复、超时或故障后保持安全暂停，不在重启时自动抢回输入。

| 场景 | 模拟器真实结果 |
| --- | --- |
| 上、中、下三个位置 × 左右 × 三方向 | 18 次均收到对应应用动作，每次恰好一个真实返回回调 |
| 左手柄高度设为 0 | 左侧窗口撤下，右侧保留；左侧边缘走系统返回，从原内移位置滑动也没有应用动作，未回退成内移手柄 |
| 正常恢复，再次开启 | 区域与额度还原，辅助功能主进程 PID 不变；不修改辅助功能设置即可重新开始试用并确认 |
| 停止应用 | 进程退出后窗口释放，原额度自动还原；遗留记录可由独立恢复页清理 |
| 主线程阻塞 | 原额度与窗口均恢复，随后左右上、中、下的系统返回通过；一次实测约 3.83 秒，不是系统深睡时的墙钟保证 |
| 额度守护被结束 | 输入窗口暂停，系统返回通过；额度仍有恢复记录，重新绑定守护后还原 |
| Shizuku 服务退出 | 本次额度守护也随之退出；应用暂停窗口，系统返回通过。额度没有立即还原，重启 Shizuku 后由恢复入口补做 |
| Shizuku 与额度守护同时结束 | 左右上、中、下的系统返回均通过，记录保留；重新启动 Shizuku 后恢复额度 |
| 未确认的试用超时 | 自动停止替换并还原，未出现内移窗口；系统返回通过 |
| 其他操作将额度改成 1100 | 恢复未覆盖这个冲突值，窗口已撤下，系统返回可用；解除冲突后可继续恢复原值 |

## 手柄优先（2026-10-28）

入口为「设置 → 系统手势共存 → 手柄优先（实验）」，使用 Android 10 起提供的 `setSystemGestureExclusionRects`。手柄贴边，申请区域随实际触摸窗口存在；不修改系统导航模式或左右热区参数，不需要 Shizuku 或本地系统设置写入权限。

每侧申请高度最多 200dp；有多个启用手柄时平分额度，保留各自垂直位置。常规长度和边距留在偏好中，关闭实验即可恢复。状态栏、缺口和底部强制手势区域避让；系统实际批准范围以设备验证为准。重叠手柄仍采用现有窗口顺序，建议错开位置。

独立的 `:recovery` 进程内增加绑定守护，仅接受本应用 UID 的会话。主线程每秒确认输入窗口后续期，超时约 4 秒时保存不参与备份的安全暂停标记，并仅结束同 UID、名称精确匹配的本应用主进程。进程退出后系统释放其窗口；独立恢复页可执行相同的手动暂停。安全暂停期间不重建任何手柄，用户明确选择继续后才恢复，避免进程自动重启时干扰第一下返回。暂停标记写入失败时仍尝试停止主进程并报告失败，不宣称已持久暂停。锁屏等临时场景正常撤回窗口，解锁后重新检查，避免误判为故障。触摸反馈使用缓存的模式状态，不逐帧读取暂停文件。

| 主线程阻塞 30 秒注入 | 原排除区域已生效后注入；约 3.5 秒触发安全暂停并结束主进程，左右系统返回通过 |
| 独立守护进程被终止 | 健康主进程退回共存，排除区域移除，左右系统返回通过 |
| 手动恢复与重新启用 | 独立恢复页退出优先模式；浅色、深色页面均能清除暂停并重新启用 |
| 熄屏和解锁 | 熄屏移除排除区域；解锁重新检查并建立窗口，左右输入回到应用 |

10 月 28 日阶段的 OPPO 未连接，后续已在 11 月 1 日补做上述受控真机输入验证。多版本、长时间使用、存储错误、系统服务异常与耗电表现仍待验收；守护阈值不是深睡或系统故障时的墙钟保证。新的手柄优先模式不能称为全高接管，旧的全高方案限制继续适用。

复现脚本随源码保存在 `tools/test_handle_priority.py`，使用 Python 标准库。先安装主 APK 和测试 APK，打开主应用一次，再指定专用模拟器运行，例如：

```powershell
python tools/test_handle_priority.py --serial emulator-5560 --scenario sparse_moves --output ../work/handle-priority
```

ADB 需在 PATH 中，也可用 `--adb` 指定路径；独立 ADB 服务可通过 `--adb-server` 指定。坐标测试限定为用户 0、1080 × 2400、420 dpi 的模拟器。脚本会暂时更改本应用偏好和模拟器的无障碍服务配置，并在结束时恢复快照；`stall` 会注入主线程阻塞。它明确拒绝真机，不应移除设备检查来做日常手机测试。恢复测试还覆盖了恢复进程持有旧偏好缓存的情况，恢复按钮不依赖该缓存判断是否停用手柄。

恢复页使用独立进程和独立任务栈，避免再次打开桌面恢复入口时，Android 将主界面带到前台。复现脚本在点击恢复按钮前检查当前前台页面。UIAutomator 查询控件时会短暂挂起其他无障碍服务，重新启用测试因此等待系统实际恢复原排除区域，再检查真实滑动回调。

## 全高 Shizuku 接管实现

- 使用 Shizuku shell UserService 临时写入当前用户的左右返回热区设置；试用限时 30 秒，左右边缘均须实际完成校准，用户确认后才持续接管。
- 接管前保存原始值，通过应用自身权限实际演练本地恢复，再创建新的试用事务。独立的「恢复系统手势」桌面入口运行于独立进程，可在 Shizuku 不在线时使用已授予的本地权限恢复。
- 主线程健康心跳、守护超时、取消标记和跨进程锁用于处理故障；输入法、锁屏、排除应用等场景先归还系统，条件满足后重新申请。底部主页和多任务不由应用接管。
- 恢复按左右原值分别处理；外部改动的值不会被直接覆盖。故障时保留恢复记录，不以设置写入成功代替真实手势验证。

Shizuku 停止时其 UserService 可能一起退出，独立恢复进程也不能抵抗卸载或清除应用数据。恢复权限被撤销、应用数据不可用、外部存储锁不可用，或系统设置调用超时且无法确认已停止时，恢复不能保证成功。预留权限为系统级 `WRITE_SECURE_SETTINGS`，范围不限于手势；实现代码只使用固定的两个手势设置键。

## 已验证

隔离环境为 Android 16 / API 36 模拟器（1080 × 2400，420 dpi），Shizuku 13.6.0；不代表其他模拟器版本或手机厂商兼容。

- 构建通过；恢复数据与边界测试 25 项、Shizuku 和事务检查 46 项；守护超时恢复做过 30 次循环。
- 左右各三个滑动方向、手柄外返回、拖回取消、30 秒试用、正常停止、底部主页与多任务经过模拟器操作验证。
- 测试过应用强制停止、Shizuku 停止、锁屏、键盘、旋转、应用排除及导航方式变化等场景；独立恢复页在接管期间可恢复设置，左右系统返回均实际触发。
- 模拟器重启及应用更新后的自动恢复经过独立实验；广播不是必达保障。原值为空和左右不对称的原值均做过恢复检查。
- 现有功能浅色及深色回归各 56 项，动效检查 27 项通过。

测试结束后已归还模拟器的原始系统设置、辅助服务配置和临时授权。部分故障测试的耗时只反映该模拟器当次结果，不构成时限保证。

## 尚未完成

### OPPO 真机兼容探测（2026-10-27）

经用户同意，连接 PMX110 / Android 17（API 37），在原有双侧手势导航下进行短时测试。原始左右热区设置均不存在，SystemUI 诊断显示两侧各 105px。测试前备份相关设置与旧版应用配置，先启动独立的限时恢复脚本；未重启手机、未切换导航模式，未操作其他应用的授权。

将 `back_gesture_inset_scale_left/right` 临时写为 `0` 后，读回均为 `0`，SystemUI 的两侧宽度均显示为 `0px`，但实际左右返回仍然触发。保持亮屏后分别从两侧最外边缘、内移 1px 和 8px 重测，六次均未抑制系统返回。测试结束后恢复键的不存在状态，两侧真实返回再次通过；导航模式、其他无障碍服务配置及临时亮屏设置按原值核对。

只读检查该机 SystemUI 发现，厂商的 `SideGestureDetector` 另有 `AppSettingsHandler` 控制分支，读取厂商设置提供器中的 `disable_gestures`。提供器检查厂商签名或 `oplus.permission.OPLUS_COMPONENT_SAFE`；该权限在本机为 `signature`。这说明不能把 AOSP 热区参数的读回当成这台手机的接管证明，也不能把厂商控制通道当成已有的普通应用恢复能力。**本轮未写入厂商控制项，未开放 OPPO 全高接管。**

主 APK 曾成功更新；用户随后在手机上卸载了它。后续重新安装主 APK 和测试组件时，系统安装会话持续停留在已提交、未完成状态；已请求取消本轮会话，未通过重启系统处理。因此本机的 Shizuku 接管、独立恢复页和崩溃恢复尚未完成验收，不能引用模拟器结果代替。结束核查时两项应用均未安装。

下一步应优先探测随窗口生命周期释放的手势排除区域，先验证手柄范围内的无冲突操作；全高排除能否获准仍需实测。若继续研究厂商控制通道，必须先解决普通应用的独立恢复能力，再允许写入，不能仅依靠 Shizuku 守护。

Android 13 / 15 覆盖、两小时持续切换及待机、真实主线程 ANR、完整的写入超时与延迟副作用注入、存储满、卸载/清除数据后的外部恢复、恢复资料导出及高刷真机校准尚未完成。系统设置调用超时后的潜在延迟写入仍需进一步处理与验证，因此不能声称所有竞态都已安全解决。恢复入口的可达性目前由用户手动确认，不能证明所有厂商桌面均可访问。

在这些验收完成并经对应设备校准之前，不开放真机双侧接管，不发正式版。调试 APK 可用于模拟器开发，不能作为正式安装包推荐。
